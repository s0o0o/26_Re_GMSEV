## 기존 문제와 변경

기존 외형은 로그인 선택을 세션에만 반영했다. 게임 안에서 수정할 UI·서버 요청 계약·영속 저장이 없어 재접속 시 선택을 보존할 수 없었다.

공용 클럽하우스의 옷장 버튼/W로 편집 화면을 열고 캐릭터·털색·눈·목도리를 네 방향으로 비교한다. 기존2캐릭터/90조합을 사용하며 제공된 장식 전부를 착용 가능하게 만든 작업은 아니다. 미리보기 draft와 실제 외형은 분리하고 적용 후 서버 저장 성공 통지를 받아야 월드 외형이 바뀐다. 저장 중에는 중복 적용·닫기를 막고 실패/timeout/연결 종료를 알려준다.

## 처리 흐름과 변경 위치

1. native `wardrobe_panel.hpp`/공통 `wardrobe_client_state.hpp`: 버튼/W→편집→요청21. viewport/letterbox의 논리 입력 좌표, 기존 글꼴·색·블러를 유지한다.
2. 서버 `wardrobe_server.hpp`/`wardrobe_rules.hpp`: 본인 연결·거점·유효값·요청ID·재전송을 확인한다. world 잠금 밖에서 외형 저장을 실행한다.
3. `appearance_odbc.hpp`/`appearance_sql.hpp`: 사용자 승인된 별도 PLAYER_APPEARANCE 테이블을 공통 DB mutex/parameterized SQL/트랜잭션으로 읽고 쓴다. 기존 위치/능력치 테이블·프로시저는 변경하지 않는다.
4. 성공 시 확정 외형을 갱신하고 본인/관찰자에게 변경23, 본인에게 결과22를 보낸다. 늦게 입장하는 클라는 기존 ENTER 외형 필드를 받는다. 프로토콜 v5이므로 모든 제품을 같이 빌드한다.
5. 다음 로그인에서 DB 저장 외형 우선, 행이 없으면 기존 로그인 선택, DB 오류는 실패로 구분한다. 기존 전용계정900001299로 저장 후 새 서버/클라 프로세스의 복원을 실제 확인했다.

## 검증과 한계

전체46회귀 및 생산 클라 코드의 wire/UI·화면 크기/상태 검사를 수행했다. 실제 DB 검사와 메모리 대역 검사는 명세에 따로 기록한다. 실제 DB 외형1행을 남겼으며 새 계정 생성/자동 삭제는 없었다. 미리보기는 production client.cpp 기반 렌더러 출력이며 일반 exe에 사람이 OS 입력을 한 캡처로 부르지 않는다.

추가300명 혼합 부하의 최초 실패(274명/유지 미완료)는 보존했다. 이전 main1회와 현재본2회 같은 조건 재검사는 모두300명/15초/EOF300 통과했지만 최초 원인을 확정하지 못했다. 현재 두 실행의 외형 read최대3/4ms를 최초 실패에도 적용해 추론하지 않는다. #41의 장시간/다른 상황과 #10 과거 크래시 원인은 해결로 확대하지 않는다.

독립 UI 검토는 옷장 범위 ship. 저장 중 단축키 안내와 연결 종료 탭 입력 불일치를 고치고 다시 검증한다. 기존 HUD의 긴 이름/SPEED 겹침은 별도 후속이며 이번 옷장이 만든 문제가 아니어도 기록한다. 최종 빌드/재검증 결과는 명세와 이슈에서 실행 종료 후 확정한다.
