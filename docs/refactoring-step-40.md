[#44](https://github.com/s0o0o/26_Re_GMSEV/issues/44), 부모 [#41](https://github.com/s0o0o/26_Re_GMSEV/issues/41), [명세](specs/load-throughput-scene.md), [실측](test-results/throughput-scene-2026-11-13.json).

## 실제로 다른 플레이어는 어떻게 보이나?

사용자 요청으로 실제DB와 서버에 관찰자1명+테스트 플레이어20명을 접속시켰다. 다른 플레이어20개 객체를 수신하고10개의 서로 다른 타일에 배치된 프레임을 저장했다. 위치·닉네임·외형·이동은 모두 서버 패킷으로 전달받았으며 가짜 ENTER나 좌표를 렌더에 주입하지 않았다.

현재는 플레이어끼리 같은 칸에 겹칠 수 있어20명이20개의 구분된 모습으로 보이지 않고 닉네임도 겹친다. 테스트용 Guest01~20과2개 캐릭터/외형을 달리 지정하고 작은 이동 경로를 적용해 관찰했다. 이는 scene profile에만 적용되며 일반300명 부하 동작은 유지했다.

캡처 도구 초기화가 실패하여 독립 SFML 테스트 창에 **생산 client.cpp의 로그인·패킷 처리·client_main 렌더링을 사용**했다. 따라서 실제 네트워크 게임 장면이지만 일반exe를 OS 도구로 찍은 스크린샷이나 수동 ID/닉네임/커마 버튼 전체 검증으로 부르지 않는다. 창 프레임을 이미지로 저장한 경로는 `build/tests/live-multiplayer-scene.png`다.

## 무엇을 추가·수정했나?

- `bounded_load.cpp`: 접속300회가 실제로 끝나는 시간, 최대 접속 시도 간격/루프 시간, 이동 큐 삽입/본인 응답/미응답, 수신 바이트/패킷 카운터 추가.
- 응답의 같은 이동 토큰을 중복해서 받았을 때 응답 수를 더하지 않도록 수정했다. 이것은 계측 정확도 수정이지 서버 처리량 개선이 아니다.
- `live_client_scene.cpp`: 기존 테스트 계정으로 생산 클라 함수를 실제 서버에 연결하고 프레임 저장. `run-live-scene.ps1`은 기존 listener가 있으면 중단하고 자신이 띄운 프로세스만 정리한다.
- `analyze-load-trace.ps1`: 새 처리량 필드를 기존 로그인·종료 trace 분석과 함께 보여준다. 계정/스키마를 추가 변경하지 않았다.

## 실제300명 재사용 부하 결과

| 조건 | 로그인 | ramp(300회 시도) | 이동 큐 삽입/본인 응답 | 최종 결과 |
| --- | --- | --- | --- | --- |
| trace OFF | 300 | 4220ms | 6053 / 5654 | EOF300, 통과 |
| trace ON + 회귀 동시 실행 | 300 | 4566ms | 5518 / 4341 | EOF0, 종료timeout300 실패(교란 조건) |
| trace ON 단독 재실행 | 290 | 4388ms | 13216 / 10328 | 로그인timeout1·종료timeout299 실패 |

단독 실행에서는 DB 처리 최대16ms에 비해 로그인 완료 큐 최대7515ms, world 입장 대기 최대294ms를 관측했다. 입력이 서버 큐에 도착하기 전/후 시각과 OS scheduling은 더 분리해야 한다. trace의 동기 파일 flush 자체도 부하를 만들 수 있으므로 trace가 유일한 원인이라고 확정하지 않는다.

설정한10ms는 매번 보장되는 간격이 아니었다. trace-off에서도 실제 최대 간격31ms/루프25ms였다. 종료 시 미응답399개는 클라이언트 출력 버퍼·네트워크·서버 대기와 측정 시점 영향을 모두 포함한다. 서버에399개 쌓였다는 의미는 아니다. cleanup 수신 바이트는 이 응답 카운터에 더하지 않는다.

로그인timeout은 이번에290명에서 재현했으므로 부모#41은 계속P1이다. 서버가 종료된 크래시가 아니며, 기존 #10의 직접 원인 확정은 아니다. 다음은 대량 이동 송신과 로그인 완료가 공유하는 큐/worker 처리 예산·격리 설계를 검토한다. 제한시간 증가나 world 잠금 제거로 통과시키지 않는다.

## 검증

회귀36개/중복 이동 토큰 검사/모의TCP, 실제 scene peer20명 유지·정리, 최신 생산 클라 Release와 캡처 harness 빌드 통과. 최초 Winsock include 오류와 캡처 helper 초기화 실패는 명세에 기록했다. 이번 변경은 서버 코드를 바꾸지 않아 서버를 새로 빌드하지 않고 직전 main Release 서버를 사용했다. 일반 그래픽exe의 수동 로그인 재시도(#19), 장시간 부하/CPU profiler는 미검증이다. 계정 총600개는 그대로 보존했다.
