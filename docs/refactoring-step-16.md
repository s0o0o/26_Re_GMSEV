# 16. 로그인 시간 초과 대응 (#19)

## 확인된 사실과 한계

첨부 화면은 TCP 접속 이후 클라이언트가 10초 동안 로그인 완료를 확인하지
못했다는 의미다. 이 문구만으로 DB 장애나 패킷 불일치를 단정할 수 없다.
조사 시 로컬 3000 포트에서 실행 중인 게임 서버는 확인되지 않았다.
실제 DB 로그인 요청은 계정 생성/갱신을 유발하므로 임의로 실행하지 않았다.

## 변경

- `game_database.cpp`: ODBC statement 생성 시 쿼리 제한 5초를 요청한다.
  이전에는 연결 제한만 있고 쿼리 대기 제한이 없었다. 설정 실패 시 해당
  statement를 해제하고 DB 오류 경로로 보낸다. 제한은 개별 쿼리 기준이며
  공유 mutex 대기/여러 쿼리를 포함한 로그인 전체 5초 보장은 아니다.
- `client.cpp`: 전송 바이트/수신 바이트를 기록해 전송 지연, 무응답,
  일부 응답 뒤 완료 누락을 구분한다. 잘못된 응답은 timeout을 기다리지
  않고 프로토콜 불일치로 즉시 실패 처리한다. 실패 후 선택 유지/재시도는 유지한다.
- `myserver.cpp`: 수신, DB 조회 시작/끝, 완료 작업 등록, 성공 응답 제출을
  `[LOGIN]`으로 기록한다. 완료 작업 등록 실패 시 명시적인 실패 응답을 보낸다.
  처리한 로그인 완료 작업 객체도 해제한다.
- `game_session.cpp`: 즉시 송신 등록 실패 시 세션과 Winsock 오류를 기록한다.

쿼리 제한과 연결 제한은 별개라는 근거:
[Microsoft 쿼리 시간 초과 문서](https://learn.microsoft.com/en-us/troubleshoot/sql/database-engine/performance/troubleshoot-query-timeouts).

## 검증

`tests/run-login-screens-preview.cmd`에 실제 클라이언트 함수와 SFML
루프백 모의 서버를 연결하는 테스트를 추가했다. 임시 포트만 사용하며 DB는 쓰지 않는다.

- 닉네임/캐릭터가 담긴 58바이트 로그인 요청 확인.
- 정상 아바타 정보 + 로그인 완료를 수신하면 GameScreen 진입.
- 합쳐 온 패킷과 첫 1바이트/나머지로 분할된 패킷 모두 처리.
- 거절/잘못된 프로토콜/무응답/일부 응답/연결 종료 후 커마 복귀 및 재연결.
- 서버·클라이언트 Release x64 빌드와 기존 회귀 테스트 8개 확인.
- 실제 게임 서버 + 실제 DB에서 사용자 장애가 해소됐는지는 아직 미확인이다.

## 사용자 환경에서 이어서 확인

1. 실행 중인 서버/클라를 종료하고 둘 다 새 빌드로 다시 실행한다.
2. 서버 초기화가 끝난 후 로그인한다.
3. 실패하면 서버의 `[LOGIN]` 줄들과 `[DB]` 오류, 클라의 `[LOGIN] Timeout`
   줄을 함께 확인한다. 이슈 #19는 실제 환경 확인 전까지 열어 둔다.

`Received` 없음은 서버 수신 경로/실행 파일/포트 확인이 필요하다.
`DB lookup begin` 이후 `end`가 없으면 DB 실행 또는 공유 연결 대기 구간이다.
`Success response submitted` 이후에도 실패하면 송수신 오류/프로토콜을 확인한다.
이 로그는 위치를 좁히는 단서이며 그 자체로 최종 원인 확정은 아니다.
