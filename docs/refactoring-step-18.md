# 18. 몬스터 초기화 지연과 준비 로그 (#20)

## 왜 오래 걸릴 수 있었나

기존 `monsterInit`는 시작 시 200,000개 세션 각각에 Lua 상태와 표준 라이브러리를
만들고 같은 `npc.lua`를 읽었다. 시작/완료 사이 로그가 없어 진행과 정지를 구분하기
어려웠다. 실제 사용자 프로세스의 스택을 채집한 것은 아니므로 특정 대기 원인을
전부 확정한 것은 아니다. 이 대규모 생성 비용을 코드에서 확인해 개선했다.

## 변경

- `startup_config.hpp`: 로컬 기본 몬스터 수 2,000. 환경변수
  `GMSEV_MONSTER_COUNT`로 0–200,000 선택. 잘못된 설정은 시작 전에 오류 처리.
  이는 월드 몬스터 밀도 변경이며 예전 20만 규모가 필요한 경우 명시적으로 설정한다.
- `monsterInit(count)`: 250개마다 진행 수/경과시간 표시.
  Lua 상태 생성, 파일 로딩, 실행, set_uid 호출 실패를 검사하고 원인을 표시한다.
- 맵과 몬스터 초기화 이후에 소켓 bind/listen을 시작한다.
  bind/listen 실패도 검사한다. 초기화 중 TCP만 연결되고 응답을 못 받던 상황을 줄인다.
- 워커 시작 후 `[READY] Server ready. Login is available on port 3000` 출력.
  이제 로그인 가능 여부는 이 줄을 기준으로 확인한다.
- `--startup-check`: DB 접속과 네트워크 없이 실제 몬스터/Lua·맵 생성 후 종료.
  검사 또는 초기화 실패 시 생성한 Lua 상태를 정리한다.

## 검증

- 실제 Debug 검사 실행: 기본 2,000마리 Lua 초기화 547ms, 맵 초기화 완료, 종료 0.
  한 번 측정한 로컬 결과이며 다른 환경의 시간 보장은 아니다.
- npc.lua 없는 작업 폴더에서 명확한 로딩 오류 및 종료 1.
- 최대 초과 설정(200001)에서 시작 전 거부 및 종료 1.
- 수량 기본/0/최대/음수/공백/문자/오버플로 경계값 검사 추가: 회귀 테스트 총 10개.
- 서버 Debug·Release x64 빌드 확인. 기존 변환/링크 경고는 남아 있다.
- 실제 DB 로그인/부하테스트와 20만 마리 전체 초기화는 실행하지 않았다.
  로그인 장애 #19는 별도로 실제 환경 확인이 필요하다.

## 사용

기존 서버를 종료하고 새 Debug 빌드로 실행한다. 기본 설정은 별도 입력이 필요 없다.
20만 마리가 필요한 경우 Visual Studio 디버깅 환경에
`GMSEV_MONSTER_COUNT=200000`을 지정한다. 그 경우 초기화 시간/메모리 비용도 커진다.
Visual Studio 작업 디렉터리는 `npc.lua`가 있는 서버 프로젝트 폴더여야 한다.
실행 후 `[READY]`를 보고 클라이언트를 접속한다.
