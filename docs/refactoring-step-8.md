# 8단계: 부하테스트 오류 경로와 DB 동시 접근 조사

이슈: https://github.com/s0o0o/26_Re_GMSEV/issues/10

## 조사 결론

20~30명 부근에서 종료되었다는 제보를 기준으로 코드에서 아래 결함을 확인했다.
당시 덤프/콜스택과 실행 로그가 없으므로 그 종료의 직접 원인을 확정한 것은 아니다.

| 확인한 문제 | 수정 |
| --- | --- |
| IOCP 실패 처리에서 송신 over를 삭제한 후 아래 코드가 다시 참조 | 처리 완료 시 즉시 continue |
| 로그인 실패 패킷이 default로 들어가 메시지 창과 무한 루프 실행 | 실패를 기록하고 해당 연결 정리 |
| 로그인 전에는 connected=false라 실패 소켓을 닫지 않음 | 소켓 열림 상태를 별도로 추적 |
| 실패한 접속 슬롯을 재사용하며 이전 I/O와 섞일 수 있음 | 시도마다 슬롯을 한 번만 할당 |
| 무작위 DB 계정 ID를 사용해 여러 테스트 연결이 같은 계정 사용 | 테스트 슬롯 번호를 계정 ID로 사용 |
| 서버 이동 응답의 move_time이 미초기화 | 본인 이동 응답에 요청 시간을 반환, 다른 알림에는 0 |
| 32비트 시간을 64비트 현재 시간에서 그대로 빼서 잘못된 지연 산출 | 32비트 차분으로 래핑 처리 |
| DB 연결 하나의 쿼리/commit/rollback을 여러 스레드가 동시에 호출 | 모든 DB 진입점을 같은 mutex로 보호 |
| 서버 송신 완료 및 즉시 실패 시 할당 메모리 미해제 | 두 경로에서 전송 객체 해제 |
| 로그인 전 접속 종료에도 기본 ID/능력치로 DB 저장 | 로그인 완료 상태였을 때만 저장 |

DB mutex는 안정성을 위한 임시 직렬화다. DB 처리량을 높이는 커넥션 풀은 아니다.
조회→생성→재조회 전체를 하나의 트랜잭션으로 묶은 것도 아니므로 같은 계정의
동시 신규 생성 경쟁은 남아 있다. 업데이트/생성의 일부 ODBC 반환값 검사도 후속 과제다.

## 왜 접속 증가가 멈출 수 있었나

스트레스 도구는 측정 지연이 100/150ms를 넘으면 접속 증가를 제한한다.
초기화되지 않은 시간 값과 잘못된 시간 차분은 잘못된 지연을 만들 수 있었다.
이는 프로세스 종료와 별도로 접속 증가 중단을 설명할 수 있는 코드 결함이다.
지연 수치는 기존처럼 관측값에 조금씩 접근하는 지표이며 즉시 측정 RTT 자체는 아니다.

## 검증

- tests/stress_error_test.cpp는 실제 NetworkModule.cpp를 포함하여 로그인 거절,
  null/실패/0바이트 완료, 잘못된 ID, 중복 로그인 응답, 중복 종료를 검사한다.
- tests/session_packets_test.cpp는 이동 요청 시간 반환과 기본값 0을 검사한다.
- 서버 x64 Debug/Release 및 스트레스 도구 Release 빌드를 확인한다.
- 실제 DB를 대상으로 30/100명 동시 접속하는 실행은 수행하지 않았다.

테스트는 x64 Native Tools Command Prompt에서 저장소 루트 기준으로 실행한다.
출력 디렉터리는 각 프로그램을 먼저 빌드해서 생성하고 NDEBUG를 정의하지 않는다.

```bat
cl /nologo /EHsc /std:c++17 tests\stress_error_test.cpp /Fe:stress_test\x64\Release\stress_error_test.exe /Fo:stress_test\x64\Release\ /link user32.lib
stress_test\x64\Release\stress_error_test.exe
```

송신/소켓 종료의 모든 동시성, 서버 세션 ID 재사용, 스트레스 도구 전체 종료
절차와 일부 좌표 공유의 데이터 경쟁은 이번 수정으로 모두 해결되지 않는다.
접속 수 한계나 당시 크래시 재현 성공을 주장하지 않는다.

## 재시험 방법

서버와 스트레스 실행 파일을 최신 빌드로 맞추고, 테스트용 DB에서 수행한다.
이번 도구는 ID 0부터 기존 행을 조회/이동/저장하고 없는 계정을 생성하므로
실제 플레이 데이터가 있는 DB에서 실행하면 그 데이터가 변경될 수 있다.
서버 콘솔, 스트레스 도구의 [LOAD] 메시지, 종료된 프로세스 이름, 예외 코드와
콜스택을 함께 기록하면 당시 현상과 같은 원인인지 좁힐 수 있다.
