# 39단계: 10053의 발생 시점과 혼합 부하 계측

부모 [#41](https://github.com/s0o0o/26_Re_GMSEV/issues/41), 완료한 계측 하위 [#43](https://github.com/s0o0o/26_Re_GMSEV/issues/43), [명세](specs/mixed-load-diagnostics.md), [측정값](test-results/mixed-load-2026-11-13.json).

## 기존 코드에서 무엇을 몰랐나?

기존 서버의 `Send submission failed ... 10053`만으로 로그인 중인지 종료 뒤인지 알 수 없었다. 콘솔 테스트는 `shutdown(SD_SEND)` 직후 읽지 않고 모든 소켓을 닫았다. 서버가 보내던 이동 알림이 남은 상태와 충돌할 가능성이 있었다. 또 전원 로그인만 확인하면 정상으로 보이던 테스트가 종료 대기 지연은 검사하지 않았다.

## 바뀐 위치와 흐름

- `shared/load_trace.hpp`: `GMSEV_TRACE_FILE` 지정 시에만 별도 파일에 시각·session·connectionId·이벤트·측정값을 기록한다. 여러 thread의 줄이 섞이지 않게 잠근다. 계정 ID/닉네임/DSN/패킷 내용은 넣지 않는다.
- `myserver.cpp`, `game_session.cpp`, `iocp_operation.hpp`: 로그인 수신→DB 결과→world commit→완료 큐→세션 잠금→입장, 즉시 송신 실패, EOF/disconnect/저장 성공 반환을 같은 연결로 추적한다. 오래된 연결과 재사용된 숫자 session을 혼동하지 않는다.
- `world_state.hpp`: 기존 재귀 잠금을 유지하며 opt-in 상태에서20ms 이상 대기/보유를 기록한다. 잠금을 없애거나 순서를 바꾸지 않았다.
- `bounded_load.cpp`: `mixed/separate`와 `drain/immediate`를 선택한다. 기본은 수신 drain이다. 측정 종료→송신 EOF 통보→최대5초 남은 수신 읽기→서버 EOF 확인→닫기 순서다. cleanup에서 버린 바이트는 게임 성공 수치에 더하지 않는다. 유지 성공이어도 drain 오류/timeout이 있으면 최종 실패한다.
- 실행/분석 script: 두 승인 계정 범위만 선택 가능하다. COUNT/고유 ID 수를 매개변수 SELECT로 검사하고, trace를 분석해 종료 전/후 송신 오류와 단계 대기를 구분한다.

## 실제 DB 4회 결과

각300명, 로그인 제한45초, 전원 로그인 뒤15초 유지. 5초 종료 제한도 늘리지 않았다.

| 조건 | 로그인/유지 | 종료 EOF | 10053 송신 실패 | 최종 결과 |
| --- | --- | --- | --- | --- |
| 기존 계정·분리·즉시 닫기 | 300/300 | 미검사 | 300, 모두 종료 시작 이후 | 기존 gameplay 기준 통과, 정상 종료 보장 아님 |
| 기존 계정·분리·drain | 300/300 | 300 | 0 | 통과 |
| 기존 계정·혼합·drain | 300/300 | 300 | 0 | 통과 |
| 신규 계정·혼합·drain | 300/300 | 0, timeout300 | 300, 모두 종료 시작 이후 | **실패** |

신규 계정 실행은 전원 로그인까지37.481초, 총57.522초였다. 각 연결에서 로그인 수신→ready 최대1274ms, 그중 완료 큐 최대1202ms, DB 조회/생성 전체 구간 최대16ms를 관측했다. 클라이언트가 첫 시도를 시작한 시각과 개별 서버가 로그인 패킷을 처리하기 시작한 시각은 다르다. 이 숫자만으로 전체37.5초를 특정 서버 잠금이나 DB 원인으로 돌릴 수 없다.

신규 실행은 수신 drain도 부하에서5초 안에 끝나지 않을 수 있음을 보여준다. 10053을 무조건 정상 종료 경고로 숨기지 않는다. 대기열/이동 요청·응답 처리량, 접속 시도 간격, 송수신 완료 지연을 다음 단계에서 분리 계측한다. 처음의291 로그인 timeout 자체는 재현하지 못했으므로 부모 #41은 닫지 않는다.

모든 실행에서 disconnect 저장 성공 반환300건을 trace로 확인했다. 실제 DB의 최종 위치/스탯 readback이나 서버 전체 I/O drain을 검증한 것은 아니다. 사용자 승인으로 새300개를 추가해 테스트 계정은 **총600개**가 남아 있다. 삭제/스키마 변경은 하지 않았다. 본 작업에서 띄운 서버만 종료했다.

## 검증과 다음 작업

전체 회귀36개, 동시 trace800줄/재귀 잠금 수명 검사, 모의 TCP 혼합/분리·조각 수신·즉시종료·EOF 거절 timeout 검사, 서버 x64 Debug/Release·기존 GUI stress Debug/Release 빌드, DB 없는 startup-check 통과. C4244/LNK4098 등 기존 경고는 남아 있다. CP949 소스 보존. 실제 GUI 클라이언트 입장(#19), 장시간 soak와 서버 graceful shutdown은 미검증이다.

trace flush 자체가 스케줄링/성능에 영향을 줄 수 있다. 성능 비교를 확정하거나 기존291 timeout의 원인을 확정한 결과가 아니다. 다음은 #41의 남은 대기열/처리량 및 trace 비활성 조건 비교이며, 그 결과 뒤 #19의 실제 클라 동선을 확인한다.

미리보기는 네 실제 실행의 측정값 도표이고 게임 캡처가 아니다. 원본은 `build/tests/load-*`에 보존하며 요약 JSON은 저장소에 남긴다.
