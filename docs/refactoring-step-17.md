# 17. 로그인 연결 중단 후 세션 정리 (#19 후속)

사용자 로그에서 DB 계정 생성과 조회(Found)는 끝났지만 첫 송신부터
10053이 발생했다. 이는 연결 중단 상태에서의 송신 실패다. DB 조회 실패와는
구분해야 하며, 연결 중단을 유발한 원인까지 이 로그만으로 단정할 수 없다.

확정한 코드 문제:

- `game_session.cpp`가 즉시 WSASend 실패 후 메모리만 해제하고 세션은
  계속 사용했다. 여러 NPC 작업이 같은 죽은 연결에 계속 전송했다.
- WSARecv 등록 즉시 실패는 검사하지 않았다. 이런 실패는 완료 통지가
  오지 않으므로 기존 IOCP 완료 경로만 기다리면 세션 정리가 누락될 수 있다.
- 로그인 성공을 보내지 못해도 ST_INGAME 등록/지도 전송/주변 NPC 활성화를 진행했다.

변경:

- 세션에 원자적 `transportFailed`/`disconnectStarted`를 추가했다.
  첫 즉시 송신 실패만 기록하고 이후 송신은 차단한다. pending receive는
  shutdown으로 깨워 정리 경로로 유도한다.
- 수신 등록은 성공/IO_PENDING만 정상으로 인정하고 즉시 실패 시 호출자가 disconnect한다.
- 로그인 완료 전에 끊긴 세션은 게임에 넣지 않는다. 로그인 응답 송신이 즉시
  실패하면 지도 전송과 NPC 활성화 전에 정리한다.
- disconnect 중복 호출은 첫 호출만 처리해 소켓 중복 닫기/저장을 방지한다.
- 성공 로그도 '응답 제출'이 아닌 '송신 등록 승인'으로 구분했다.
  이는 클라이언트 수신 확인을 의미하지 않는다.
- 서버 DB 조회 경과시간과 클라 실패 이유/경과시간/송수신량을 기록한다.

검증:

- 실제 Winsock+IOCP 루프백 테스트에서 수신 pending, 수신 완료, 송신 완료와
  로그인 완료 패킷 전달을 확인했다. 실제 DB는 사용하지 않았다.
- 유효하지 않은 소켓의 즉시 오류 뒤 반복 100회 송신 차단과 수신 실패를 확인했다.
  강제 오류는 10038이며, 사용자 환경의 10053 자체를 재현한 테스트는 아니다.
- 기존 테스트 포함 회귀 테스트 총 9개.
- 사용자 실행 구성인 서버 Debug x64와 Release x64를 모두 빌드했다.
- 클라 Release 빌드 통과. 기존 Debug exe는 링크 시 잠겨 있어 덮어쓰지 않고
  `build/debug-verification/`의 별도 출력 경로로 Debug 빌드를 검증한다.
  기존 클라이언트를 종료한 후 정상 Debug 경로에서 다시 빌드해야 새 로그가 반영된다.
- 기존 공용 레지스트리/세션 ID 재사용과 모든 비동기 수명 경쟁을 이번 변경으로
  해결했다고 주장하지 않는다. 원격 클라이언트 수신 성공도 별도 확인이 필요하다.

서버·클라를 종료하고 같은 최신 코드로 재빌드해 실행한다. 계속 실패하면
서버 `[LOGIN]`(특히 `elapsed_ms`), `[NET]`, 클라 `[LOGIN] Failed`를 함께 수집한다.
이슈 #19는 실제 로그인 진입 확인까지 열어 둔다.

오류 코드 근거: [Microsoft Winsock 오류](https://learn.microsoft.com/en-us/windows/win32/winsock/windows-sockets-error-codes-2).
