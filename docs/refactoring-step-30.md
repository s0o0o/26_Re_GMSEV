# 30단계: 동시 이동·전투의 월드 상태 보호

이슈 [#32](https://github.com/s0o0o/26_Re_GMSEV/issues/32), [사전 명세·AC별 결과](specs/world-state-concurrency.md).

## 기존 문제

지난 단계의 접속 목록 잠금은 **어떤 접속 객체인지**를 안전하게 찾는 기능이었다. 그 객체의 x/y, HP, 씨앗, 이름·외형을 읽고 바꾸는 동작은 별개였다. 공격이 HP를 바꾸는 도중 다른 worker가 패킷을 만들거나 이동/시야를 처리하면 일관되지 않은 상태를 볼 수 있었다.

## 변경 위치와 처리 흐름

- `world_state.hpp`: 재귀 가능한 `WorldStateLock`과 현재 스레드의 보유 여부 검사를 추가했다. 현재 작은 맵에서는 안전성을 우선해 월드 상태 구간을 하나씩 처리한다.
- `myserver.cpp`: 이동·공격·입장·퇴장·주변 탐색·AI 작업을 같은 경계로 보호한다. 잠금 순서는 자기 completion → world → NPC/시야/sector/transport다. AI도 NPC 잠금 전에 world를 잡는다.
- `session_packets.cpp`, `game_session.hpp`, `world_events.hpp`: 패킷에 쓰는 상태와 `snapshotObject()`가 같은 보호를 받는다. 스탯 패킷 id 초기화 누락도 보완했다.
- DB 경계: 조회는 잠금 밖 → 결과 공개와 저장용 복사는 잠금 안 → 실제 저장은 잠금 밖으로 나눴다. 공격끼리의 별도 전역 attackMutex는 이제 중복이므로 제거했다. DB 호출을 그 잠금으로 막아 월드가 기다리지 않게 한다.
- Lua 인수 검증은 RAII 잠금 전에 수행해 잘못된 인수가 오류를 내더라도 잠금이 남지 않도록 했다.

## 검증

사전 명세 `98f6ece` 후 구현했다. 회귀 프로그램은 21개다.

- snapshot 단위 검사에서 쓰기 중 강제로 스레드를 양보해도 좌표/HP·씨앗 쌍과 이동·스탯 패킷이 일치했다.
- 실제 worker 4개/연결 4개에서 동시 이동·공격을 실행했다. HP 5 NPC에 유효 타격 5회, 사망 알림 1회, 씨앗 총 5개 소비를 모든 관찰자 결과와 비교했다. 종료 저장 값도 일치했다.
- DB 대역에서 월드 잠금이 풀렸는지 직접 단언했다. 최종 하네스와 snapshot 검사를 10회 추가 반복해 통과했다(추가 이동 2,080건/공격 요청 170건).
- 정상 서버 Debug/Release, DB 없는 startup-check, 문서 UTF-8·상대 링크·diff 검증. 기존 빌드 경고는 유지된다.

실제 DB·게임 UI·npc.lua와 실시간 타이머 전체 실행·장시간 부하는 미검증이다. **공통 잠금은 병렬 처리량을 줄일 수 있으며 성능 향상 작업은 아니다.** 클라이언트와 공유 프로토콜은 바꾸지 않았다.
