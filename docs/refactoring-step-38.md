# 38단계: 현재 DB 확인과 실제 300명 부하 검사

작업 [#40](https://github.com/s0o0o/26_Re_GMSEV/issues/40), [명세/실행 결과](specs/bounded-load-test.md), 미해결 조사 [#41](https://github.com/s0o0o/26_Re_GMSEV/issues/41).

## 기존 도구도 남아 있어!

`stress_test/STRESS_TEST.sln`은 기존 OpenGL 화면+IOCP 네트워크 도구다. `NetworkModule.cpp`에서 localhost:3000에 접속하고 ID를 0부터 사용한다. `GMSEV_LOAD_ATTEMPTS`로 상한을 지정하지만 **접속 시도 수**이지 성공한 동접 수가 아니다. 종료 스레드가 무한 루프에 join하므로 자동 실행/결과 수집에도 한계가 있다. 기존 파일은 보존했다.

새 `stress_test/STRESS_TEST/bounded_load.cpp`는 같은 `shared/protocol.hpp`를 사용하는 별도 콘솔 동반 도구다. 기존 GUI 실행파일을 자동화했다고 부르지 않는다. 1~300명/명시 계정 범위/로그인 제한 시간/유지 시간을 받으며, 여러 nonblocking 소켓을 단일 WSAPoll 루프에서 처리한다. 접속·로그인 완료·이동·종료를 구분하고 JSON 결과와 실패 종료 코드를 남긴다.

## 실제로 무엇을 확인했나?

- 프로젝트 DSN 연결과 메타데이터 조회 성공. 이번에는 승인받은 전용 ID `900000000~900000299`로 실제 계정 생성/저장도 실행했다.
- 실행 전 범위의 계정 수0 확인. 재시도 시 전용 범위의 행 수/고유 ID 수가 같은지 확인해 중복이면 중단한다. 기존 일반 캐릭터를 쓰지 않았다.
- **첫 혼합 부하는 실패**: 300시도 중291로그인, timeout1. 서버 종료는 아니며 병목 원인은 아직 미확정이다.
- **로그인→이동을 분리한 부하는 통과**: 300로그인/최대 동접300/15초 전원 유지/300명 본인 이동 응답. 총19.733초. 이동 응답은 각 client가 한 번 이상 받은 기준이며 전체 명령 처리량/지연 측정은 아니다.
- 클라이언트 오류 카운터는0이지만 서버에는 10053 송신 실패300행이 남았다. 종료 과정과의 관련성 및 정확한 시점은 추가 계측이 필요하다. 이를 숨기거나 서버 오류0으로 보고하지 않는다.
- 실제 DB 최종 계정 수300. 테스트 계정은 삭제하지 않았다. 서버의 정상 종료 명령이 없어 3초 대기·생존 확인 후 이번에 띄운 프로세스만 강제 종료했다. 모든 저장 완료/IOCP drain 보장은 아니다.

## 실행 방법

VS x64 개발자 콘솔에서 `stress_test\build-bounded-load.cmd`로 별도 콘솔을 빌드한다. 실제 DB 재실행은 데이터 변경을 동반한다:

```powershell
# 기존 전용 계정 재사용을 명시해야 한다. 서버 Release 빌드도 먼저 준비한다.
./tools/run-approved-load.ps1 -ConfirmAccountWrites -ReuseApprovedTestAccounts
```

새 콘솔만 직접 실행할 수도 있다. 이 경우 사전 COUNT 검사와 서버 기동/정리는 호출자가 책임져야 한다:

```bat
build\tests\bounded_load.exe 300 900000000 15 45 3000
```

`tests/run-bounded-load.cmd`는 DB 없는 모의 TCP 검사다. 조각 패킷/300명/거절/끊김/timeout/잘못된 패킷을 검사하며 전체 회귀는35개 통과했다. 기존 GUI stress Debug/Release와 생산 서버 Release 빌드도 통과했다. 클라이언트/서버 Debug는 이번에 새로 빌드하지 않았다.

원본 로그는 무시되는 `build/tests/load-*` 폴더에 보존하고 [비밀 없는 결과 JSON](test-results/load-2026-11-13.json)을 저장소에 남겼다. 미리보기는 측정값을 그린 도표이지 게임 캡처가 아니다.

다음은 #41에서 혼합 부하의 로그인 대기와 종료 송신 실패를 계측하는 작업이다. 지역 직접 좌표/패킷 전환은 그 진단 이후 이어간다. 짧은 분리 부하 통과가 최대 수용량·장시간 안정성이나 기존 #10/#19의 해결을 뜻하지 않는다.
