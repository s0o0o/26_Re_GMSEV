# 15. DB 저장 경로 안전성 (#18)

## 기존 문제

`game_database.cpp`의 `update_user_info`와 `insert_new_user`는
매개변수 바인딩 결과를 검사하지 않았다. 갱신에서는 statement 할당 실패도
확인하지 않았다. SQL 실행 자체가 성공하면 실제 갱신 행이 0개여도 true였다.
또 `update_user_info`가 받은 `damage`는 UPDATE 문에 없어서 저장되지 않았다.

## 변경한 코드와 흐름

1. DB 내부 `Statement`가 ODBC 실행 핸들을 소유하고 모든 반환 경로에서 해제한다.
   기존 로그인 조회도 같은 소유 클래스를 사용한다. 복사는 금지했다.
2. `database_write.hpp`의 공통 흐름은 준비 → 각 값 연결 → 실행 → 영향 행 수 확인이다.
   어느 단계든 실패하면 바로 중단한다. 실패한 단계와 ODBC 진단을 남긴다.
3. 저장 값은 순서가 있는 배열로 묶었다. UPDATE의 마지막 두 값은 공격력과 계정 ID다.
4. 실행과 행 수 조회가 성공하고 영향 행이 정확히 1개일 때만 성공을 반환한다.
   0개/알 수 없음(-1)/여러 행은 확인된 성공으로 취급하지 않는다.
5. DB 연결 시 자동 커밋을 명시한다. 각 저장마다 연결 전체에 보내던
   불필요한 rollback/commit 호출은 제거했다. 공유 연결 mutex는 유지한다.

자동 커밋에서는 실행 직후 변경이 반영될 수 있다. 행 수 확인에 실패했다고
이미 실행된 쓰기가 취소된다는 의미는 아니다. 이 함수들은 재시도하지 않는다.
NOCOUNT/트리거 등 실제 DB 설정이 행 수에 미치는 영향은 통합 검증이 필요하다.

관련 공식 문서:
[자동 커밋 속성](https://learn.microsoft.com/en-us/sql/odbc/reference/syntax/sqlsetconnectattr-function),
[영향 행 수](https://learn.microsoft.com/en-us/sql/odbc/reference/syntax/sqlrowcount-function).

## 검증과 범위

- `database_write_test.cpp`: 준비 실패, 9개 각각의 바인딩 실패, 실행 실패,
  행 수 조회 실패, 0/-1/2행 반환과 정상 1행을 모의 객체로 검사한다.
- 공격력/계정 ID를 포함한 값 순서와 실패 후 실행하지 않는지 검사한다.
- 회귀 테스트는 기존 7개에 추가해 총 8개다.
- 서버 Release x64 빌드 통과. 기존 형 변환/런타임 라이브러리 경고는 남아 있다.
- 실제 DB 접속/계정 생성/스키마 변경/부하 실행은 하지 않았다.
  따라서 과거 20–30명 동접 종료 문제를 해결했다고 단정하지 않는다.

외형 영구 저장은 이번에 추가하지 않았다. 다음 단계에서 스키마와
계정별 저장/불러오기 및 기존 커마 선택과의 우선순위를 함께 다뤄야 한다.
