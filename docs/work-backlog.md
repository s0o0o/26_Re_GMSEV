# 후속 작업 큐

2026-11-13 재검토. 기준 main `5f4759e`, 정리 이슈 [#42](https://github.com/s0o0o/26_Re_GMSEV/issues/42). P1/P2/P3는 작업 순서이며 장애의 잠재적 심각도 자체를 뜻하지 않는다. 아래는 **계획**이지 해결·테스트 실행 결과가 아니다.

## 작업 순서

추가 진행 [#44](refactoring-step-40.md): 실제DB/생산 클라 코드의21명 동접 장면과 처리량 카운터를 확인했다. 별도 실행에서290명 로그인timeout이 재현됐고, DB최대16ms/로그인완료큐최대7515ms를 관측했다. #41은P1 유지하며 다음은 대량 이동과 로그인 완료 큐/worker의 처리 예산·격리 설계다. trace 오버헤드/OS scheduling을 원인과 구분한다. #19에는 실제 생산코드 GameScreen 증거를 추가했으나 일반exe UI 재시도 검증은 남아 있다.

진행 기록: [#43 계측·콘솔 종료 개선](refactoring-step-39.md)은 완료했다. 기존계정 drain 비교는 송신실패0이지만, 추가 승인된 새계정300명 혼합은 종료5초 제한에서 실패했다. #41의 다음 범위는 대기열/처리량·접속 시도 간격·trace 비활성 조건 비교다. #41 전체를 해결로 닫거나 #19보다 후순위로 내리지 않는다. 테스트 계정은 승인된 두 범위에 총600개가 남아 있다.

#41에서 크래시·현재 1명 로그인 실패·데이터 손상이 확인되거나 사용자가 다시 제보하면 해당 문제를 P1로 승격한다. 원인 미확정 상태에서 시간 제한만 늘리거나 테스트를 분리한 것으로 해결 처리하지 않는다. 이슈 간 대기는 외부 입력 없이는 아무 작업도 못 한다는 의미의 차단 상태가 아니라 작업 순서다.

## #10이 아직 열린 이유

과거 GUI stress의 삭제 후 접근/로그인 거절 무한 대기/실패 소켓 정리와 서버 DB 직렬화 등의 코드 결함은 main에 수정되어 있다. 하지만 당시 덤프/콜스택이 없고 20~30명 프로세스 종료의 직접 원인은 미확정이다.

[#40 실측](test-results/load-2026-11-13.json)은 **새 별도 콘솔 실행기**의 검사다. 기존 GUI 도구 전체를 실행한 것이 아니며, 혼합 부하는 시간 초과됐지만 서버 프로세스 종료는 관측되지 않았다. 분리 부하 300명·15초 통과만으로 과거 크래시를 해결했다고 닫지 않는다. 기존 GUI의 종료 절차/공유 좌표 경쟁은 별도 검토 대상이다.

남은 완료 체크:

- 최신 빌드와 전용 계정에서 기존 GUI의 30명→100명→300명 단계 시나리오, 관측 시간과 반복 수를 착수 명세로 고정한다.
- 크래시 시 프로세스/예외 코드/덤프 또는 콜스택을 수집하고 수정과 회귀를 연결한다. 재현되지 않으면 실행 조건·한계와 함께 **미재현**으로 기록하고, 해결 확정이 아닌 종료 여부를 별도로 판단한다.
- #41의 혼합 부하 지연·종료 송신 오류와 같은 원인인지 근거로 구분한다. 중복이라면 대표 이슈와 검증 근거를 연결한 뒤에만 중복 종료한다.

## #19가 아직 열린 이유

모의 서버에서 생산 클라의 성공/실패/분할 수신은 검사했고, 서버의 즉시 송수신 실패와 중복 정리도 보강했다. 사용자 로그에서는 DB 생성·조회 뒤 10053이 발생했지만 연결 중단의 최초 원인은 미확정이다.

최근 콘솔에서 실제 DB 로그인 300명은 확인했다. 그러나 **실제 그래픽 클라이언트의 GameScreen 진입**을 검증한 것은 아니다. 기존 본문의 과거 미검증 설명은 이 구분으로 갱신한다.

남은 완료 체크:

- 실제 최신 서버/그래픽 클라/DB로 로그인→커마→게임 진입을 관찰하고, 정상 위치/외형을 확인한다.
- 같은 빌드의 재접속과 실패 후 재시도를 검사하고 클라 실패 이유·송수신량과 서버 connectionId/시각을 연결한다.
- #41의 오류와 같은 경로면 진단을 재사용한다. 10053 숫자가 같다는 이유만으로 원인이 같다고 단정하지 않는다.
- 추가 수정이 필요하면 회귀를 추가한다. 정상 경로만 확인하고 현재 재현되는 timeout을 남겨둔 채 종료하지 않는다.

실제 DB 테스트 계정 생성/저장은 데이터 변경이다. #40의 `900000000~900000299`와 #41에서 추가 승인된 `900001000~900001299`에 각300개, 총600개가 남아 있다. 후속 실행마다 범위·중복 검사와 재사용/변경 내용을 명시한다. 계정을 자동 삭제하거나 기존 일반 캐릭터로 대체하지 않는다.
